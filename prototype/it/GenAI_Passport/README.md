# 生成AIパスポート：適切・不適切切り替え型Drill

問題フォーマット案 **v0.1.0** と、添付教材の第1・2・4章から2問ずつ選んだ計6問のサンプルです。内容・形式のレビュー用で、まだ確定仕様ではありません。

- [問題データ：sample_questions.json](data/sample_questions.json)
- [形式の定義：question-bank.schema.json](question-bank.schema.json)（JSON Schema Draft 2020-12）

## 目的と分担

1. このサンプルで、IT用の問題フォーマットと抽出ルールを決める。
2. 確定した形式で、ほかの生成AIを使って教材を調整する。
3. Codexは、確定仕様に従って切り替え型エンジンを開発・検証する。

今回作成したのは教材形式・サンプル・仕様説明です。エンジンや実行用HTML、既存Drillとの接続は未実装です。

## 基本単位：一つの文脈と二つの設問文

1レコードは一つのテーマ・文脈を表します。同じレコードに、適切を問う設問文と、不適切を問う設問文を明示して持たせます。エンジンによる文末の自動置換や文章からの判定は行わない設計です。

**プールの分類は、そのレコードの設問の文脈に対して適切かどうか**です。単独で事実として正しい文でも、問われた対象に合わなければ不適切になり得ます。同じプール内・同じレコード内だけから抽出し、章全体から無関係な候補を混ぜません。

今回は正解が一つの4択に限定し、両方向の出題のために各プールを3件以上とします。サンプルは各3件、合計36候補です。適切・不適切を切り替えた12種類の設問を構成できます。

各3件は最低構成なので、3件を抽出する側の顔ぶれは固定です。根拠のある候補を4件以上確保できる場合は、その側の組合せも変えられます。ただし、件数より正確さを優先し、両プールの件数を揃える必要はありません。各5件・6件などの件数目標は設けず、最低件数を満たすためにも不確かな候補は追加しません。信頼できる候補をどちらかのプールで3件確保できないテーマは、出題対象から外し、要確認事項としてJSONの外に報告します。

| キー | 必須 | 内容 |
| --- | --- | --- |
| `format` | 必須 | `it-polarity-pool` 固定。ほかの形式との識別用 |
| `schema_version` | 必須 | この案では文字列 `0.1.0` |
| `exam_id` | 必須 | 今回は `GENAI_PASSPORT` |
| `questions` | 必須 | テーマごとのレコード配列 |
| `questions[].question_id` | 必須 | テーマを識別する安定したID |
| `chapter` | 必須 | 章番号。正の整数 |
| `topic` | 必須 | テーマ名。正式なシラバス分類とは別に管理する仮の学習単位 |
| `stems.appropriate` | 必須 | 適切なものを一つ選ぶ設問文 |
| `stems.inappropriate` | 必須 | 適切でないものを一つ選ぶ設問文 |
| `explanation` | 必須 | テーマ共通の解説。どちらの出題でも成立する説明 |
| `pools.appropriate` | 必須 | その文脈で適切な候補。3件以上 |
| `pools.inappropriate` | 必須 | その文脈で不適切な候補。3件以上 |
| 各候補の `option_id` | 必須 | 候補を識別する安定したID |
| 各候補の `text` | 必須 | 選択肢本文 |
| 各候補の `explanation` | 必須 | なぜ適切／不適切なのか。誤りの場合は正しい考え方も説明 |

### 作問時のルール

- 両方の設問は、同じ対象・条件・文脈を問います。否定形にした結果、別の知識や状況を問う設問にならないようにします。
- どの候補が抽出されても分類が変わらず、どの組合せでも正解が一つになるように作ります。「最も適切」という相対比較に依存させません。
- 候補は単独で読める文にし、「上記」「ほかの三つ」「1と2」「すべて正しい」のように表示位置やほかの候補へ依存させません。
- 同一レコード内で、本文の重複や、同じ意味の候補を適切・不適切の両方へ入れることを避けます。組合せによる正解の手がかりもレビューします。
- 候補本文に「正解」「不正解」を埋め込みません。`isCorrect` や固定の `correct_answer` も教材データには持たせません。
- 適切プールの候補が常に「テストの正解」とは限りません。不適切を問う回では、適切プールの3候補は誤答になります。
- 解説は「この選択肢が正解だから」ではなく、内容が適切／不適切な理由を書きます。選ぶべき候補かどうかは、出題方式から別に判定します。
- 本文・解説はプレーンテキストとし、改行はJSONの `\n` を使います。HTML、Markdown、実際の認証情報は入れません。
- 章・topicを変えても、同じ内容ならIDは維持します。ID内の章番号は初回採番時の情報です。別の知識を問う内容へ変える場合や候補の意味を変える場合は、新しいIDを採番します。文章表現だけの修正ではIDを維持します。
- 今回の候補IDの `A` / `I` は適切／不適切を見分ける作成上の便宜です。エンジンはID文字列を解析せず、プール所属を使います。所属変更は実質的な意味の変更として新しい候補IDにします。

## エンジンに渡す抽出ルール案

| 出題方式 `mode` | 設問文 | 適切プールから | 不適切プールから | 正解の条件 |
| --- | --- | --- | --- | --- |
| `appropriate` | `stems.appropriate` | 1件 | 3件 | 適切プール所属 |
| `inappropriate` | `stems.inappropriate` | 3件 | 1件 | 不適切プール所属 |

各プール内では重複なしで抽出し、抽出後の4候補をシャッフルします。候補のプール所属と、その回に選ぶべき候補かを区別します。

例えば分類と回帰の問題で `GAIP-CH01-Q007-I01` が出た場合、その文は常に不適切な説明です。ただし、適切を問う回では誤答、不適切を問う回では正解です。解説の内容は変わりません。

この問題の抽出例は次のとおりです。表内は候補IDの末尾のみを表示しています。実際には4候補の順序もシャッフルします。

| 出題方式 | 抽出する候補の例 | 選ぶべき候補 |
| --- | --- | --- |
| 適切を問う | A01・I01・I02・I03 | A01「予測したいものが問い合わせの種類なので、この課題は分類である。」 |
| 不適切を問う | I01・A01・A02・A03 | I01「種類に数字を割り当てているため、この課題は回帰である。」 |

出題方式を決めてから、その回の候補を組み立てます。同じ演習内では、問題へ戻っても候補や順序を変えません。途中で出題方式を変更する場合は新しい演習として開始する設計案です。

問題数はテーマ数で数えます。同じ演習で、同じ `question_id` を適切・不適切の両方で重複出題しないことを初版の既定とします。出題方式の切り替えUIや、適切／不適切を混在させる設定・比率は未確定です。

### 開始前に検証すること

- 必須フィールド、型、両方の設問文、各プール3件以上、空文字の禁止。
- 読み込む全バンクにわたる設問ID・候補IDの一意性。
- 同じレコード内の候補本文の重複。前後空白・Unicode正規化などで同じになる本文も検出します。
- 適切1＋不適切3、または適切3＋不適切1で、選ぶべき候補が必ず一つになること。

不足・不整合がある問題で、別テーマから補充したり、同じ候補を複製したりはしません。問題IDと理由を表示して開始を止める方針です。

JSON Schemaは構造を確認するためのものです。IDの一意性、本文の正規化後の重複、文意の正しさ、設問文の意味までは保証しません。別の検証処理・内容レビューが必要です。

### 既存Drillとの境界

これは教材の作成・保管形式です。既存の `option_1`〜`option_4` を持つ固定4択JSONや、`conf_JLPT_N2_LK.json` と同じ形式ではありません。現在のローダーへ直接渡しても動作しません。

今後のIT用アダプターで、出題する回に限って `question` と `options[{text, isCorrect, rationale}]` などの既存エンジン形式に変換する方針です。画面・回答・即時解説・自信度・結果画面を再利用し、既存N2の読み込み経路は維持します。

動的な出題内容を再確認できるよう、記録には少なくとも以下を残す必要があります。

- 元バンクの識別情報、形式バージョン、設問ID、出題方式。
- 実際の設問文、表示順に並んだ候補ID・本文・プール所属・解説、正解候補ID。
- 学習者が選んだ候補IDと表示位置、未回答の区別、既存の時間・自信度・理解度など。

乱数のseedや問題IDだけでは、教材更新後の再現に不足するため、出題内容のスナップショットも保存する方針です。既存CSVはこれらの動的項目をすべて保持できないため、IT用の出力形式・保存方法はエンジン開発時に定義します。共通の結果処理にそのまま渡せば記録できる、という状態ではありません。

>
> 各テーマに、同じ前提で適切／不適切をそれぞれ一つ選ぶ設問文と、適切候補3件以上・不適切候補3件以上を用意してください。各候補に、その内容が適切／不適切な理由と必要な訂正を説明してください。どの組合せでも正解が一つになるようにし、単独で読めない候補、無関係な候補、意味の重複を避けてください。正誤の文章表現・長さだけから答えが分かりやすくなっていないかも確認してください。
>
> 候補数より正確さを優先してください。適切候補は、根拠を説明できる内容だけを採用し、件数合わせの言い換えや条件の拡大で増やさないでください。不適切候補も、設問に関連する誤解を扱い、誤りの理由と正しい考え方を説明してください。両プールの件数は揃える必要はありません。
>
> 両方向の4択には各3件以上が必要です。信頼できる候補を3件確保できないテーマは、無理に補完せず、出題対象から外して要確認事項としてJSONの外に報告してください。
>
> 各5件・6件は義務にしません。最小件数を満たすためにも不確かな候補を追加せず、不適切候補も、無関係・曖昧・誤りを説明できないものは採用しないでください。
>
> 既存の意味を保つ表現修正ではIDを維持し、別の内容・意味へ変更する場合や新規追加時は新しいIDを付けてください。`isCorrect` や固定の正解番号は追加しないでください。難易度や公式シラバス分類を根拠なく作らないでください。法令やサービス仕様などは、適用条件と確認時点に注意してください。
>
> 問題データはコメントなしのJSONで返してください。出典・内容の要確認事項や形式の改善提案があれば、JSONの外に分けて報告してください。フォーマットの変更案をデータへ無断で混ぜないでください。
